# Change report: a before/after page for every data change

## Why

The campus data changes without anyone looking. The monthly scrape commits the
college's edits straight to `main`, and its only trace is a bot commit and a
`git diff --stat` in the run summary. When the college redrew the Natural Lands
segments in October 2026, nothing told us; we found out by accident, and the
next scheduled scrape would have failed silently except for one email to
whoever last edited the workflow.

Working through that change, a hand-built page — the Heath Creek trails as
published against the new assembly, dashed before and solid after, the moved
stretches highlighted, close-ups where it mattered, and a table of lengths —
made the change obvious in seconds. Drew wants that page generated
automatically, deterministically, for every change to the data.

The reference is that page: <https://claude.ai/artifact/MiZrP9DN1ot8quWwu2tJkM>
(its generator, a one-off, is reproduced in spirit below; it knew only four
trails).

## Goals

1. **A report page for any change to the published data**, generated by a
   script in this repo from two versions of it: what is committed, and what a
   run is about to commit. Same inputs, byte-identical page.
2. **Before/after, interactive.** Toggle the old and new states; old dashed,
   new solid; what was dropped and what was added marked distinctly; a close-up
   for each area that changed; hovering or selecting a changed place ties its
   shape on the map to its entry in the list.
3. **Text changes too**, not just shapes: places added, removed, renamed, and
   any field that changed (name, description, categories, parent, rules,
   links, citations, walk, floors, length…), prose shown as a word-level diff.
   A rename changes what people search for in AAO; a description is a card.
4. **Notification without gating.** Data keeps flowing to `main` unattended.
   Whenever the published files on `main` change — a scrape's commit or a
   merged pull request alike — a **GitHub release** is published, "Campus data
   2026-11-01", whose notes summarise the change and link to the report. Anyone
   who watches the repo for releases is notified; nobody else is bothered. The
   releases are the complete log of data changes.
5. **The failed run is covered.** A scrape whose data changed but fails
   `verify.py` commits nothing and releases nothing — but it still builds the
   report and attaches it to the run, because that is the run where a person
   has to act.
6. **Pull requests get it too.** The scrape workflow's existing PR dry run
   builds the same report, so a change like PR #27 can be reviewed from it.

## Non-goals

- Gating the data behind review. No bot PRs for data changes. (`watch.yml`'s
  bot PR stays as it is: that is for a person to act on a watched page.)
- Issues. Drew does not want an issue per change.
- A tiled basemap in the report. The page is a self-contained HTML file with
  inline SVG drawn from our own data, so it renders the same years later, offline,
  and as a downloaded run artifact. (The Pages site's own tiles change daily and
  would not show the campus as it was.)
- Reporting changes to the tiles, the style or OSM. This is about the
  college's data and our overrides.
- `routing.json`. It is rebuilt from the data; a change there is a consequence,
  not news. (A one-line note that it changed is fine.)

## Anti-goals — failure even if it technically works

- **Noise.** A release or report when nothing a person would care about
  changed. No timestamps anywhere in the page or the data; nothing generated
  per run that differs between two runs on the same data.
- **A report that lies.** It must be computed from exactly the files being
  published — `map.json`, `map.geojson`, `data/*.geojson` — not from a separate
  model of them. If the page and the commit disagree, the page is wrong.
- **The report breaking the data.** A bug in the report must never stop a good
  scrape from committing. Data first; report and release are best-effort after
  it, and a failure there shows as a failed step, not a lost update.
- **A page only its author can read.** It is for a person who did not watch
  the change happen: plain words, real place names, units in metres.

## How it works

### Inputs and the diff

The script compares a **before** and an **after** state of the published files:

| File | What it contributes |
| --- | --- |
| `map.json` | Places by `id`: every field, for the per-place list |
| `map.geojson` | Each place's full geometry (MultiPolygons and all lines, which `map.json`'s single-ring `outline` loses) |
| `data/*.geojson` | Context: walkways, roads, the campus boundary, the segments layer — geometry with no id |

*Before* is a git revision (default `HEAD`), read with `git show`; *after* is
the working tree. That is exactly the scrape's situation (it has just
regenerated the files and not yet committed) and a PR's (base vs head, by
checking out head and passing the base revision).

Places are matched by `id`. The result has these kinds of change:

- **Added** / **removed** place.
- **Renamed.** Ids derive from names, so a rename shows up as one place removed
  and one added. Pair a removed and an added place from the same layer whose
  geometry overlaps (or whose points are within a few metres) and present the
  pair as a rename, with its other field changes.
- **Changed fields** on a place present in both. Compare every key; present
  each changed key as before → after. Long text (`description`, `rules`) as a
  word-level diff. Lists (`categories`, `links`, `citations`, `departments`,
  `floors`) as items added and removed.
- **Moved geometry.** For a place whose geometry changed, measure what moved:
  stretches of the old shape more than **3 m** from the new one are *dropped*,
  stretches of the new more than 3 m from the old are *added* (this is the
  prototype's `off_runs`, sampling segment midpoints, using
  `geometry.distance_m`). A change entirely within 3 m — re-digitising noise,
  coordinate jitter — is not shown as a move. It is still listed as "geometry
  changed, under 3 m" so the page never hides a byte that changed.
- **Context changes.** Context features have no ids. Compare them as sets of
  geometries (after the scrape's 7-decimal rounding, which already makes them
  stable); show context lines that appeared or disappeared, faintly, and count
  them per layer.

### The page

One self-contained HTML file. No external requests except, optionally, a
Google Fonts stylesheet (the page must still render correctly without it).

- **Header:** the date, a one-paragraph plain summary ("4 trails redrawn in the
  Natural Lands; 36 bike racks added"), and the counts.
- **Overview map**, inline SVG on a flat local projection: water, walkways and
  building outlines as a quiet background; every changed place drawn old
  (dashed) and new (solid); dropped stretches and added stretches highlighted in
  two distinct colours; a scale bar.
- **Close-ups**, one per area of change. Cluster changed geometry by proximity
  (changes within about 150 m of each other share a close-up) and frame each
  cluster with padding. Areas with no change get none. A change that is a whole
  new layer (36 bike racks) is one overview, not 36 close-ups.
- **Toggles:** before, after, both. Hover or select a changed place, on the map
  or in the list, and the other highlights.
- **The list:** grouped by kind (added, removed, renamed, changed), each place
  a small card with its id, layer, and the changed fields before → after.
- **Lengths and areas** where relevant: a trail's length before and after, as
  the reference page's table did.
- Light and dark themes; works at phone width.

The reference page's look — the survey-sheet layout, dashed/solid convention,
pink for dropped and dark for added — is the starting point, not a constraint.

### Determinism

Same before and after inputs → byte-identical HTML. Sort every list (places by
id, clusters by position, fields by name), round coordinates written into the
SVG to a fixed precision, embed no time. The date in the title comes from an
argument, not the clock. A test runs the script twice on fixture data and
compares bytes, and another compares against a committed golden file.

### One release workflow, two ways in

Every change to the published files on `main` goes through one new workflow,
`release.yml`. It is the only thing that builds a release, so a scrape's change
and a merged pull request's are reported the same way.

GitHub does not start workflows for pushes made with a workflow's own
`GITHUB_TOKEN`. That rules out a single push trigger: the scrape's commit would
never fire it. (It is also why the tile workflow does not rebuild after a
scrape's commit today, despite its comment saying so; see below.) So:

- **A person's push to `main`** — a merged PR — that touches `map.json`,
  `map.geojson` or `data/*.geojson` triggers `release.yml` on `push`, with the
  range `github.event.before`..`github.sha`.
- **The scrape**, after pushing its commit, starts `release.yml` with
  `workflow_dispatch` (which `GITHUB_TOKEN` may do), passing the commit before
  and the commit it pushed.

`release.yml` then:

1. Builds the report for that range. If the published files did not actually
   change between the two commits, it stops: no page, no release.
2. Commits the page to `main` as `site/changes/<YYYY-MM-DD>.html` (a second
   change the same day: `-2`, and so on), rebasing and retrying on a race as
   the scrape's commit step does. The scrape does not watch `site/**`, so this
   cannot loop, and `GITHUB_TOKEN`'s push starts nothing else.
3. Starts the tile workflow with `workflow_dispatch`, so the Pages site — which
   `build-tiles.sh` now builds with `site/changes/` copied in — goes live with
   the page at `https://stolaf.dev/campus-map-data/changes/<name>.html`. The
   same dispatch fixes the existing gap: a scrape's data reaches the tiles in
   minutes, not at the next daily run.
4. Publishes the release: tag `data-<YYYY-MM-DD>` (same suffix rule) on the
   data commit — the one that changed the files, not the page commit; title
   "Campus data <YYYY-MM-DD>"; notes with the plain summary, counts by kind,
   the report link and the commit link, short enough to read in a
   notification email. `gh release create`, `contents: write`.

The page goes live a few minutes after the release, when the tile deploy
finishes. That lag is acceptable; the release notes stand on their own.

Pages are committed rather than built on deploy because the Pages deploy
replaces the whole site from `dist/` every time: a page must be reproducible
on every later deploy, and keeping them in git puts the history of reports
next to the history of data.

### The scrape workflow

`scrape.yml`, after `build_routing.py`:

1. Builds the report against `HEAD` (or, on a PR, the base branch) whether or
   not `verify.py` passes — it must run on the failing path too — and puts a
   one-line pointer in the run summary.
2. On a **failed verify** or a **pull request**, uploads the page as a
   workflow artifact. A failed run still fails; the existing failure email is
   the alert, and still goes to whoever last edited the workflow's schedule.
3. On a **good scheduled or dispatched run that commits**, pushes the data as
   today, then dispatches `release.yml` with the before and after commits. The
   scrape commits only data; `release.yml` owns the page and the release.
4. Nothing after the data push can undo it. A failure in the report or the
   dispatch shows as a failed step; the data stays committed.

`tiles.yml` gains a `workflow_dispatch` caller in `release.yml` (it already
accepts `workflow_dispatch`) and its comment about the scrape's push is
corrected. `build-tiles.sh` copies `site/changes/` into `dist/`.

The README's "commit history is the change log" section gains a paragraph on
releases and reports.

### Settled in review (Claude's calls)

- **A PR's before** is the base branch's committed files (`origin/<base>`),
  and its after is what the dry run regenerated with the PR's code. That shows
  the PR's change plus any live drift in the college's data since `main` was
  last scraped; the summary says so when the live data has moved, which the
  scrape's existing `--check` comparison can tell.
- **No loop.** `release.yml` triggers on the published data files only, not
  `site/**`, so its own page commit never re-triggers it; and a
  `GITHUB_TOKEN` push starts no workflow anyway.
- **One release per push.** A merged PR whose push changes the data gets one
  release for its whole range, however many commits it had.
- **Dates are UTC**, from the run, passed to the script as an argument.
- **No reports backfilled** for changes before this ships.
- **A failed run's report** is an artifact only. The existing failure
  notification is the alert; this design does not add another channel.

## Constraints

- Python 3.13, stdlib only, beyond the two dependencies the project already
  allows (`pyyaml`, `pmtiles`); `pyproject.toml` explains why. No new
  dependencies for diffing, HTML or SVG. The page's script is inline vanilla JS.
- Reuse `scripts/geometry.py` (`distance_m`, `length_m`, `polygons`,
  `positions`) instead of reimplementing geometry.
- Follow the repo's style: module docstrings that explain why, comments
  explaining what and why, TDD, `ruff`, deterministic output.
- Pinned action SHAs in workflows, as the existing ones are.
- The page is under a few hundred KB for an ordinary change; the 36-rack
  addition and the trail redraw are the two realistic sizes to check against.

## Left to the builder

- Module layout (one `scripts/report.py`, or a diff module plus a renderer).
- The exact clustering and padding, the projection code, SVG styling and
  palette, as long as the conventions above hold.
- The word-diff algorithm (`difflib` is available).
- How hover/select is wired, and whether the list collapses.
- The summary sentence's wording, generated from the counts and layers.
- Test fixtures: small hand-built before/after states are fine; the two real
  changes of October 2026 (bike racks, PR #26; the Heath Creek remap, PR #27)
  make good end-to-end checks.
